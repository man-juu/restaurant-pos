# 05. Data Model

Logical model. Final column types and names are fixed when each migration is written. Everything below is for PostgreSQL. Tables for later-phase features (combos, loyalty, budgets, offline sync, customer-facing booking) are specified when their phase begins.

## 1. Conventions

| Topic | Rule |
| --- | --- |
| Primary keys | UUIDv7 generated by the server (time-ordered, index friendly) |
| Tenancy | Every tenant-owned table has `tenant_id uuid not null`, an index starting with `tenant_id`, and row-level security (see 4) |
| Money | `bigint` in the smallest currency unit, plus `currency char(3)` where it can vary. IDR scale is 0. |
| Quantities | `numeric(18,4)` in the item's **base unit** |
| Unit costs | `numeric(18,6)` per base unit (moving averages are fractional); line totals are rounded to whole minor units by the rule in 6 |
| Time | `timestamptz` in UTC. Sales and stock documents also carry `business_date date` computed from the outlet timezone and cutoff |
| Soft delete | Master data uses `is_active` or `archived_at`. Business documents are never deleted, only reversed |
| Audit columns | `created_at`, `created_by`, `updated_at`, `updated_by`, and `version int` for optimistic locking |
| Status fields | `text` with a `check` constraint listing allowed values (easier to evolve than native enums) |
| Names | Translatable text lives in `*_translations(entity_id, language, name, description)` |
| Document numbers | Per tenant, outlet, type and year, allocated from a counter row locked in the same transaction |
| Composite FKs | Critical references use `(tenant_id, id)` so a row cannot point at another tenant's row |
| Idempotency | `idempotency_keys(tenant_id, key, request_hash, response_ref)` unique on `(tenant_id, key)` |

## 3. Ledger rules (inventory)

1. `stock_movements` is append-only. Updates and deletes are revoked from the application role; corrections are new movements with `reverses_id`.
2. `stock_balances.qty` equals the sum of `qty` in `stock_movements` for the same key, always. A nightly job and a test assert this (invariant I-1).
3. Each movement belongs to one document line; a document posts all its movements in one transaction.
4. Consumption picks batches by earliest `expiry_date` (FEFO), ties by `received_at`. A sale consuming across several batches creates several movements.
5. Moving average: on a receipt, `new_avg = (old_qty * old_avg + recv_qty * recv_cost) / (old_qty + recv_qty)`. Consumption never changes the average. When quantity on hand is zero or negative, the next receipt sets the average to the receipt cost (invariant I-2: average is never negative).
6. Production output cost: `sum(component value) / actual_output_qty` (invariant I-3: value consumed equals value produced plus recorded yield loss).
7. Transfers: out at source average cost, in at the same unit cost at destination; in-transit value is reported separately (invariant I-4: tenant total quantity is unchanged by a transfer).
8. Negative stock is allowed only for sales by default and always creates an alert.
9. Valuation at any past date is the sum of movement values up to that date.

## 4. Row-level security (pattern)

```sql
ALTER TABLE stock_movements ENABLE ROW LEVEL SECURITY;
ALTER TABLE stock_movements FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON stock_movements
  USING (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid);
```

Applied to every tenant table by a migration helper. A test enumerates all tables with a `tenant_id` column and fails if any lacks the policy or `FORCE`. The admin path adds a second permissive policy keyed on `app.is_platform_admin` for the few tables the admin console must read.

## 5. Indexing guidelines

- Leading `tenant_id` on every index of a tenant table.
- Ledger: `(tenant_id, outlet_id, item_id, business_date)` and `(tenant_id, doc_type, doc_id)`.
- Batches for FEFO: `(tenant_id, outlet_id, item_id, expiry_date)` partial on remaining quantity above zero.
- Sales reporting: `(tenant_id, outlet_id, business_date, channel_id)`.
- Audit: `(tenant_id, at desc)` and `(tenant_id, target_type, target_id)`.
- Large append-only tables (`stock_movements`, `audit_log`, `sales_lines`) are candidates for monthly partitioning if volume warrants it; not at launch.

## 6. Rounding policy

1. Unit prices and costs keep their precision.
2. Line total = `round_half_up(qty * unit_price)` to whole minor units.
3. Document totals sum line totals; tax is computed on the document taxable base, then rounded once.
4. Any difference between a computed and a rounded figure goes to a rounding line, never to hidden decimals.
5. IDR cash payments may round to a configurable step (for example Rp 100) with the difference recorded as a rounding adjustment.

## 7. Retention

| Data | Retention |
| --- | --- |
| Financial and stock ledgers, sales documents | At least the statutory bookkeeping period **(verify with an accountant)** |
| Audit log | Same as ledgers |
| Sessions | 30 days after expiry |
| Notifications | 90 days |
| Customer contact data | Until consent is withdrawn or the tenant requests deletion |
| Deleted tenant | Export offered, then purge after a defined grace period; backups age out by retention |
